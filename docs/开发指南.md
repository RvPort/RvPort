# RvPort 开发指南

[English](development.md) | 简体中文

## 架构与边界

API 和 worker 复用后端代码，通过 `RVPORT_APP_MODE` 分工。PostgreSQL 保存业务状态与任务记录，RabbitMQ 投递任务消息，Redis 提供会话、缓存和广播；对象存储保存制品。工具通过受控子进程和版本化 JSON 协议与后端衔接。

源码主要位于 `backend/src/main/java/cn/rvport/backend/`，测试位于对应的 `src/test/`。jOOQ 源码位于 `src/generated/java/`。数据库变更由 Liquibase 管理，禁止仅修改生成类型而忽略 schema。

各语言统计范围、排除理由与当前缺口见 [测试与覆盖率范围](测试与覆盖率范围.md)。

## Docker 中构建和单元测试

所有命令从项目根目录执行。宿主机只编辑文件、调用 Docker 和读取导出的报告；编译、测试、代码生成和依赖安装均在容器中执行。使用专用容器或 volume 保存输出，不挂载宿主机依赖缓存目录。

后端单元测试镜像只包含构建阶段，不要求先构建全部分析工具：

```powershell
docker build --target unit-test -t rvport-backend-unit:local -f backend/Dockerfile .
docker run --name rvport-backend-unit --memory=6g --cpus=2 -e MAVEN_OPTS=-Xmx1536m rvport-backend-unit:local
docker cp rvport-backend-unit:/workspace/backend/target/surefire-reports ./unit-reports
docker cp rvport-backend-unit:/workspace/backend/target/site/jacoco ./coverage-reports
docker rm rvport-backend-unit
```

容器执行 `mvn -B clean verify`。命令失败时先保存报告，不把失败记录标记通过。若测试阶段失败导致覆盖率报告未生成，应记录未生成原因；不能用此前版本报告代替。重复执行前先导出上一轮报告，清理本次创建的同名已停止容器。

构建默认使用 Maven Central。需要更换下载入口时，可传入 `--build-arg MAVEN_MIRROR_URL=https://受信任的镜像地址`；基础 JDK 镜像可通过 `--build-arg JAVA_IMAGE=镜像引用` 设置。替换入口应核对镜像摘要与版本，不修改全局 Docker 配置，也不关闭 TLS 校验。

后端 JaCoCo 对整体和包设置行、分支覆盖率 90% 门槛；排除项为自动生成的 jOOQ 类型。保留的 Python 脚本及其他自有工具也需要独立统计，不因 Java 检查通过就认定整个项目通过。

本次迁移按用户要求暂不验收前端覆盖率，前端仍执行 lint、类型检查、普通单元测试和生产构建。最终须按安装指南执行完整 Compose 构建，再以一次 `docker compose up -d --wait` 启动全部默认服务，检查健康状态、日志和业务流程。

后端附带的 Python 资源脚本在同一测试镜像中单独验证：

```powershell
docker run --name rvport-backend-python --memory=2g --cpus=2 -e PYTHONPATH=/workspace/tools/memory-order-analyzer/python rvport-backend-unit:local sh -c 'python3 -m coverage run --branch --source=src/main/resources/analysis,src/main/resources/bitcode,src/main/resources/agentruntime,agent-cli -m pytest src/test/python; test_status=$?; python3 -m coverage json -o /tmp/backend-python-coverage.json; python3 -m coverage report --fail-under=90; coverage_status=$?; if [ "$test_status" -ne 0 ]; then exit "$test_status"; fi; exit "$coverage_status"'
docker cp rvport-backend-python:/tmp/backend-python-coverage.json ./.migration-reports/backend-python-coverage.json
docker run --rm --memory=1g --cpus=1 --mount "type=bind,source=$((Get-Location).Path)/.migration-reports/backend-python-coverage.json,target=/tmp/coverage.json,readonly" rvport-backend-unit:local python3 -c 'import json; r=json.load(open("/tmp/coverage.json")); rows=[r["totals"],*[f["summary"] for f in r["files"].values()]]; assert all(s["covered_lines"]*100 >= s["num_statements"]*90 and s["covered_branches"]*100 >= s["num_branches"]*90 for s in rows), "行或分支覆盖率未达到 90%"; print("整体和每个脚本的行、分支覆盖率均达到 90%")'
```

首条命令保留测试失败状态并输出覆盖率；最后一条命令独立检查整体及每个脚本的行、分支均达到 90%，不能只用 coverage 的综合比例判断通过。任一步骤失败均不可标记通过。报告包含未被测试加载的资源脚本。

浮点扫描器：

```powershell
docker build -t rvport-fp-dev:local tools/floating-point-precision-scanner -f tools/floating-point-precision-scanner/Dockerfile.dev
docker run --name rvport-fp-unit --memory=8g --cpus=2 -e CMAKE_BUILD_PARALLEL_LEVEL=2 rvport-fp-dev:local make coverage cpp-coverage
docker cp rvport-fp-unit:/workspace/artifacts/coverage ./fp-coverage
docker rm rvport-fp-unit
```

KB Scanner 保留独立测试容器，已有分领域检查见 `tools/kb-scanner/README.md`。完整普通单元测试与全量覆盖率从仓库根目录执行：

```powershell
docker build -f tools/kb-scanner/Dockerfile.test -t rvport-kb-scanner-test:local .
docker run --name rvport-kb-unit --memory=4g --cpus=2 --network=none -e COVERAGE_FILE=/tmp/.coverage --entrypoint sh rvport-kb-scanner-test:local -c 'python -m coverage run --branch --source=kb_scanner,scripts,tools -m unittest discover -s tests/unit -t . && python -m coverage json -o /tmp/coverage.json'
docker cp rvport-kb-unit:/tmp/coverage.json ./kb-coverage.json
```

上一步成功后，继续在容器中校验源码无漏计、整体与本次受影响模块的行/分支门槛。后续代码修改时按实际影响维护 `affected`，不能通过缩小它跳过受影响代码：

```powershell
$kbGate = @'
import json
from pathlib import Path
r = json.load(open('/report.json'))
owned = {p.as_posix() for root in ('kb_scanner', 'scripts', 'tools') for p in Path(root).rglob('*.py')}
assert owned <= set(r['files']), sorted(owned - set(r['files']))
affected = ['kb_scanner/core/metadata.py', 'kb_scanner/analyzers/candidate_usage/proofs.py']
affected += ['kb_scanner/projection/v2/' + name + '.py' for name in ('chain', 'families', 'macro_effects', 'mapper', 'multiversion', 'summary', 'test_content', 'validation')]
rows = [r['totals'], *[r['files'][name]['summary'] for name in affected]]
assert all(s['covered_lines'] * 100 >= s['num_statements'] * 90 and s['covered_branches'] * 100 >= s['num_branches'] * 90 for s in rows)
print('完整源码、整体及受影响模块的行/分支门槛通过')
'@
docker run --rm --memory=1g --cpus=1 --network=none --mount "type=bind,source=$((Get-Location).Path)/kb-coverage.json,target=/report.json,readonly" rvport-kb-scanner-test:local -c $kbGate
```

内存序分析器的覆盖率入口为容器内的 `python3 -m memory_order_analyzer.quality --output /output/本次唯一目录`，见其 [内存序开发指南](../tools/memory-order-analyzer/doc/development.zh-CN.md)。该入口独立检查全量自有源码、各语言及每个模块，不以集成测试 profile 代替单元测试。

## 数据库与代码生成

修改数据库结构时增加 Liquibase changeset，使用新的数据库验证完整初始化，再在容器中执行 `jooq-codegen` profile。设置 `RVPORT_JOOQ_JDBC_URL`、`RVPORT_JOOQ_JDBC_USER`、`RVPORT_JOOQ_JDBC_PASSWORD`；生成结果应保持 `cn.rvport.backend.jooq` 包名。

代码生成复用上面的后端单元测试镜像，依赖与产物保存在容器内部。先创建本地 `.env.codegen`，写入 `POSTGRES_PASSWORD`、`RVPORT_MIGRATION_TEST_PASSWORD` 和 `RVPORT_JOOQ_JDBC_PASSWORD` 三个变量并使用相同的临时随机口令。此文件属于本地配置，不提交到仓库。生成用数据库不暴露宿主机端口，也不复用部署数据卷。

```powershell
docker network create rvport-codegen
docker run -d --name rvport-codegen-db --network rvport-codegen --env-file .env.codegen -e POSTGRES_DB=rvport_codegen -e POSTGRES_USER=rvport_codegen postgres:18.4
docker exec rvport-codegen-db pg_isready -U rvport_codegen -d rvport_codegen
```

待数据库就绪，再执行初始化验证与生成。`LiquibaseMigrationTests` 会执行两次迁移，以验证新空库初始化与重复执行。

```powershell
docker run --name rvport-codegen --network rvport-codegen --memory=6g --cpus=2 --env-file .env.codegen -e MAVEN_OPTS=-Xmx1536m -e RVPORT_MIGRATION_TEST_ENABLED=true -e RVPORT_MIGRATION_TEST_JDBC_URL=jdbc:postgresql://rvport-codegen-db:5432/rvport_codegen -e RVPORT_MIGRATION_TEST_USERNAME=rvport_codegen -e RVPORT_JOOQ_JDBC_URL=jdbc:postgresql://rvport-codegen-db:5432/rvport_codegen -e RVPORT_JOOQ_JDBC_USER=rvport_codegen rvport-backend-unit:local sh -c 'mvn -B -s /opt/maven-cache/settings.xml -Dmaven.repo.local=/opt/maven-cache/repository -Dtest=LiquibaseMigrationTests test && mvn -B -s /opt/maven-cache/settings.xml -Dmaven.repo.local=/opt/maven-cache/repository -Pjooq-codegen generate-sources'
docker cp rvport-codegen:/workspace/backend/src/generated/java ./.migration-reports/jooq-generated
```

只有容器成功退出且报告确认通过后，才用导出的完整 `java` 目录替换 `backend/src/generated/java/`；先保存旧生成目录供复核。不要仅覆盖同名文件，否则已删除表的旧类型可能残留。重新构建测试镜像并运行完整单元测试和覆盖率，单独的数据库测试不替代单元测试门槛。导出报告后可删除此次创建的两个容器与专用网络。

## 代码与接口变更

- 移除函数或接口前检查前端、脚本、消息处理器、定时任务、反射和框架注册，不以简单文本引用数量作唯一依据。
- 产品的自动化测试、连接测试和模型测试属于业务能力；不得与测试专用设施混淆。
- 展示给用户的业务说明按协议保留中文及英文字段，例如 `suggestion`、`suggestion_en`。
- 修改实现时同步维护正常、边界和异常路径单元测试，整体与受影响模块行、可用分支覆盖率均至少 90%。
- 新增配置同步更新 `.env.example` 和安装文档；不要提交真实凭据、运行日志或环境数据。

## 协作与发布规范

### 提交信息

提交信息采用 `Type: Message` 格式。标题写为 `<type>: <English> / <中文>`，正文先写英文段落，再写对应中文段落，说明修改内容、原因和实际验证结果。

| 类型 | 用途 |
|---|---|
| `feat` | 新功能或新的对外行为 |
| `test` | 以测试、夹具或覆盖率验证为主要目的的修改 |
| `fix` | 缺陷修复，包括修复所需的配套测试 |
| `refactor` | 不改变外部行为的内部重构 |
| `ci` | CI/CD 流水线或自动化流程配置 |
| `chconf` | 非 CI 的项目、构建、运行或工具配置 |
| `docs` | 文档修改 |

实际类型仅使用以上七种简写，不使用 `feature`、`config change` 等长名称。混合变更按主要目的选择类型；多个独立目的可拆分提交。保留 `ci` 类型不代表恢复已退役的 CI 设施。使用 `docs` 也不能免除变更中可执行代码的测试要求。

以下为已完成文档校验时的提交示例；实际提交须按本次修改和验证结果填写：

```text
docs: Document contribution rules / 补充贡献规范

Document commit types, code review, branch roles, version naming,
and the Roadmap-to-release workflow. Checked content and relative links.

补充提交类型、代码审查、分支职责、版本命名及 Roadmap 到发布的流程。
已检查内容与相对链接。
```

### 代码审计

人工编写和 AI 生成、修改的代码必须遵守同一套代码审计及 PR 审查流程。审查者需检查实现是否符合需求、正确性与风险、测试是否覆盖正常和边界及异常路径，并确认适用验证结果。发现的问题须修复并重新验证后再合并；自动检查通过不能代替代码审查。

代码变更继续遵守本指南的 Docker 验证及整体、受影响模块至少 90% 行覆盖率和可用分支覆盖率要求，以及已明确的前端覆盖率暂缓验收约定。纯文档变更检查内容、链接和格式，单元测试、代码覆盖率与运行时构建不适用。

### 分支与贡献流程

`dev` 为开发集成分支，`master` 为发布分支。日常开发通过 PR 合并到上游 `dev`。

1. 在代码托管平台 fork 上游 RvPort 仓库，再将个人 fork clone 到本地。
2. 同步上游 `dev`，以它为基础创建本地主题分支并开发。
3. 完成适用验证，将主题分支推送到个人 fork，向上游仓库的 `dev` 发起 PR。
4. 在 PR 中关联对应 Issue，说明修改内容和验证结果，经过代码审查并处理反馈后合并至 `dev`。
5. Roadmap 整体完成后，通过发布 PR 将 `dev` 合并至 `master`，按版本规范发布。

这些是协作规则，不表示远端分支保护或自动化检查已经配置。

### 版本命名

版本采用“大版本.小版本.bug fix.hotfix”四段数字格式，即 `<major>.<minor>.<bugfix>.<hotfix>`。预发布版本在末尾追加 `-<类型><序号>`，例如发布候选版本的 `rc1`、`rc2`。

| 示例 | 含义 |
|---|---|
| `1.2.0.0-rc1` | 第一个发布候选版本 |
| `1.2.0.0-rc2` | 第二个发布候选版本 |
| `1.2.0.0` | 正式版本 |

这是项目的四段版本约定，不是标准 SemVer。文档规定命名格式，不据此自动修改各模块版本号。

### Roadmap、Issue 与 PR

下一阶段 Roadmap 确定后，将计划拆解为具体 Issue，写明任务和验收条件，并指派负责人。负责人在主题分支完成开发，通过关联 Issue 的 PR 交付。PR 合并至 `dev` 且验收完成后，确认并关闭对应 Issue。

面向 `dev` 的 PR 不应假定会通过关闭关键字自动关闭 Issue；合并后核对状态，必要时手动关闭。单个 Issue 完成表示该任务完成，Roadmap 整体完成后才通过发布 PR 将 `dev` 合并至 `master` 并发布。

## OpenSpec

根目录、后端、前端和三个主要扫描器分别有独立 OpenSpec 根，共六处。运行命令时明确当前项目根，不能将后端 change 应用到工具 store。规范和归档中的验证结论只代表其原版本，当前实现需要重新验证。

进行中的 change 只有在实现和验证完成后才能归档。

## Codex CHAT 的本地验收

OpenCodex 固定为 2.94.0，Bun 固定为 1.4.4；独立锁文件及四项受控修补见 [依赖说明](../backend/agent-cli/opencodex/README.md)。生产只有 worker 执行级代理路径，API 探针通过既有 RabbitMQ 分派；不新增 Compose 基础设施。开发时将 `agent-cli` 与全部 `agentruntime` 资源脚本纳入前述覆盖率 source，整体和各模块分别执行行/分支 90% 门禁。

真实 CLI 夹具位于 `backend/src/test/fixtures/agent_runtime_acceptance.py`。在当前候选镜像内运行，提供当前源码编译出的 classes/test-classes 和依赖目录；`--omit-usage --agent CODEX --wire CHAT` 验证缺失用量，`--failures-only` 验证上游错误、协议错误、超时和取消，`--custom-only --catalog <容器内 codex-fixture-model.json 路径>` 验证真实 apply_patch 文件。该测试模型只声明文本和工具能力，不声明 verbosity；生产准入仍拒绝未支持能力。

`opencodex_protocol_acceptance.py` 验证真实第三方代理的 SSE/终态/usage/交错工具，`opencodex_patch.test.js` 直接测试固定包的受修改逻辑；`opencodex_resources.py` 测量单/双实例就绪、CPU、RSS、清理和监听回收。Bun 当前 LCOV 不提供分支计数，报告应明确该限制，并列出受修改条件两侧的断言证据，不能用函数覆盖率冒充分支覆盖率。数据库和完整 Compose 的模拟模型验收另行运行，不替代单元测试。
