## Context

本文路径除明确标为仓库根目录外，均相对于 backend 根目录。本 change 属于 backend 独立 OpenSpec 根。

`ProjectWorkflowStatusService.aggregate` 先组装展示阶段，`recommended` 再依次取任意 RUNNING、列表首个可开始阶段、BLOCKED、PENDING，最终无条件返回 archive。浮点和内存序阶段位于 report 前，因此列表顺序和支线任务会改变主线导航。`report` 当前通过清单的 reportId 提前返回 DONE，可能掩盖重新生成中的任务；DONE 也无法区分人工复核进度。

已有 `CurrentFixListResolver` 根据当前输入 Context、草稿版本、发布状态和确认版本决定资格；`ReviewWorkspaceRepository.summary` 提供待复核与待修复计数。overview 在项目权限校验后的只读 REPEATABLE_READ 事务中聚合。应复用这些事实，避免再次发明报告有效性。

前端 `../frontend/src/pages/project-detail/Workflow/stageData.ts` 仍会在 KB 和 x86 状态相同且 x86 未完成时，把后端推荐 kb 改写为 x86-build。后端应返回准确推荐并提供对接说明，本轮不修改该文件。

## Goals / Non-Goals

**Goals:**

- 按当前有效主线输出确定性推荐，阶段数组重排不影响结果。
- report 就绪优先于 KB 补扫和专项分析；有效报告尚待人工处理时继续指向 report。
- 区分生成事实、人工处理事实和确认资格；有效空清单不要求制造修复。
- 维持执行权限、各分析独立条件和后续构建验证、测试顺序。
- 提供可直接联调的字段契约、状态矩阵、单元测试及独立 Docker 验收计划。

**Non-Goals:**

- 不重排展示数组，不新增跳过操作、持久化推荐游标或主线任务调度器。
- 不新增 KB、x86 或全部专项分析完成的报告前置，不修改扫描工具、模型配置、报告判定及人工确认规则。
- 不实现前端改动，不修改远程环境，不扩展 CI/E2E 平台。

## Decisions

### 1. 推荐与阶段展示、执行资格分别计算

引入独立、可纯单元测试的 `WorkflowRecommendationPolicy`，输入按阶段 ID 索引的状态、当前源码与 Context、报告复核摘要及有效清单。聚合服务负责读取事实，策略不访问数据库、不创建任务。禁止通过数组首个元素、泛用 RUNNING 优先或把所有可执行节点排序来确定主线。

`recommendedStageId` 是页面应聚焦的位置，可指向正在运行或需要人工处理的节点。`canStart` 仍回答是否可以发起该阶段执行；生成完成但未确认的 report 可以为 DONE，而推荐仍为 report。不得为了让旧选择器选中 report 而篡改其状态。

### 2. 明确优先级与回退规则

按下面顺序取第一个适用规则；仅使用与当前项目、源码和 Context 匹配的事实。

| 顺序 | 条件 | 推荐 |
|---|---|---|
| 1 | 项目基础配置未满足现有有效性要求 | project；不额外引入新的必填配置 |
| 2 | 无有效源码，或当前源码导入流程正在执行 | assets；导入失败保留可读原因 |
| 3 | 当前 Context 的报告任务已排队或运行，包括重新生成 | report；历史报告仍按原规则可读 |
| 4 | 有有效当前报告，但待复核、未确认或需重新确认 | report |
| 5 | 有当前有效非空确认清单 | manual |
| 6 | 有当前有效空确认清单 | 转后续验证分流 |
| 7 | 没有可用当前报告，但报告 readiness 允许普通生成 | report，即使 KB 未执行、运行或失败 |
| 8 | 需要修复当前报告工作区缺失等异常，且不能直接重新生成 | report；展示不可用事实，不伪造可执行 |
| 9 | 尚无报告有效输入 | kb；使用其真实运行、阻塞和可执行状态 |

已存在项目的 project 当前通常为 DONE；不新增项目创建前的 overview 接口。源码导入按既有活动源码语义处理，不自行清空旧源码或报告。仅历史导入失败且有有效活动源码时，不自动回退至 assets。

依赖、浮点、内存序、前置 x86 和环境连接任务的 RUNNING/BLOCKED 不抢占上述规则。KB 主线优先级也不是硬前置：任一已合法发布且当前有效的分析输入满足报告策略，立即进入规则 7。PARTIAL 不被自动视为失败或必须重扫，继续服从现有输入发布策略。

后续验证分流：有效空清单不再推荐 manual；依次关注 build、test，二者均有效成功后才按现有 readiness 检查 optimize、archive。当前步骤所需环境不满足时指向 env；源码或构建配置等其他缺口指向相应已有主线入口并保留真实阻塞，不启动任务。不能满足优化/归档前置时不凭空推荐其执行；无可处理动作或已完成有效归档时返回 null。成功和运行状态必须与对应源码、环境及构建验证记录匹配，历史成功不能跳过当前验证。

非空确认清单仍推荐 manual，不通过独立构建或测试成功推断人工修复完成；用户修复并更新源码后按新 Context 重算。已有独立构建和测试入口不受导航焦点约束，执行顺序保持不变。

### 3. 使用一个当前报告导航摘要

新增只读的 `workflow.reportReview` 摘要，具体契约见 [api-contract.md](api-contract.md)。保留 `workflow.currentFixList` 的结构和含义；摘要与清单共用一次解析结果，不复制其有效性规则。草稿计数只查询当前报告，不加载全部条目正文或历史列表。

报告摘要同时表达 `state` 与 `confirmationState`：存在待复核条目时 state=PENDING_REVIEW；曾确认后编辑的草稿即使仍待复核，其 confirmationState 仍为 NEEDS_CONFIRMATION。无法读取有效草稿时计数返回 null，不用 0 掩盖未知。确认清单 itemCount 不等于当前草稿待修复数量。

当前报告任务识别需要源码和 Context 身份。现有 `activeGeneration(projectId)` 只返回项目级布尔值，不能直接作为推荐依据；使用带任务及输入身份的查询或现有等价查询。有效旧报告与新生成任务并存时优先显示 GENERATING，但不因生成尝试直接取消旧清单资格；终态后重新按真实发布、草稿和 Context 规则解析。失败生成若未破坏当前有效报告，继续展示其真实复核状态，失败任务仍在任务历史可查。

### 4. Context、权限和性能

保持 overview 的项目访问校验及只读一致性事务；不查询触发者以外的个人配置或泄露模型密钥。复用 `ReportInputSelectionPolicy` 和当前清单解析结果，不通过最新时间戳选择历史成功报告。源码、语言、源架构、分析输入等导致 Context 改变时，摘要及推荐同步失效。支线仅运行不改变推荐；合法新结果发布导致 Context 改变则正常要求重新生成/确认，这与抢占不同。

复核摘要读取缺失记录应返回 UNAVAILABLE，不返回 500；禁止将历史只读报告作为有效清单。针对确认记录缺失等不一致数据，补齐明确不可用分支而非 `orElseThrow` 向外泄露。新增查询数量有固定上界，不随报告/条目数量增长，不在 overview 调用 Agent、SSH 或修改数据。

### 5. 契约和规范边界

保留 stage ID、枚举及展示排序；新增机器状态字段不要求前端立即消费。用户可见的新增业务说明必须同时具备中文与英文；本 change 的摘要优先使用机器码与既有双语说明，不新增单语文本。

同步修改 `project-source-environment` 中无条件推荐环境管理的旧场景，保留环境配置版本、ready 和连接验证规则。新能力规范集中定义主线优先级，原有可选 x86、多语言分析、报告复核与优化闭环规范仍分别负责自身有效性和执行条件。

## Risks / Trade-offs

- 前端旧覆盖规则仍可能把 kb 显示为 x86-build → 提供输入/输出联调夹具，明确后端验收以 API 为准，前端移除覆盖属于后续独立修改；不以假状态绕过。
- 导航和 DONE 含义不同可能被误解 → 契约明确 report DONE 仅表示生成，报告摘要表达人工处理；推荐不等于可立即创建任务。
- 额外读取引起 Context 混用或 N+1 → 共用只读快照及当前报告 ID，固定次数汇总，覆盖并发切换和历史混排测试。
- 新分支可能降低整体覆盖率 → 必须实际采集 JaCoCo，整体和受影响模块行/分支分别达标；不修改排除项或用旧报告补证据。
- 空清单路径可能误标验证成功 → 将验证分流与状态聚合分开测试，检查无新增构建、测试或修复记录。

## Migration Plan

1. 仅在 backend 增量实现策略、只读摘要和契约，无数据库迁移、数据清理或阶段绑定迁移。
2. 在独立本地资源执行单元测试、覆盖率与完整 Compose 验收，保存实际命令、源码版本/差异、镜像标识和输出。
3. 提供前端对接说明及夹具，不修改前端。回退后端版本可恢复旧推荐行为，不需要回滚业务数据。
